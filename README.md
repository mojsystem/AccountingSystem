# AccountingSystem

Professional Accounting System - C# .NET 10.0

سیستم حسابداری و خرید/فروش ارز برای صرافی، با **C# و .NET 10.0** و **SQL Server 2019**.
برنامه به‌صورت **وب** (ASP.NET Core Razor Pages) و **ویندوز** (Windows Forms) اجرا می‌شود و هر دو از یک هسته‌ی مشترک و یک پایگاه داده استفاده می‌کنند.

> **ارتقای خودکار:** پایگاه داده را برنامه می‌سازد و هر بار که برنامه‌ی وب یا ویندوز اجرا شود، نسخه‌ی آن را با نسخه‌ی برنامه مقایسه می‌کند و نسخه‌های باقی‌مانده را به ترتیب اجرا می‌کند؛ اطلاعات موجود حفظ می‌شود. پیش از هر ارتقا پشتیبان گرفته می‌شود (بخش «ارتقا، پشتیبان و بازیابی»).

## امکانات

- **خرید ارز از مشتری و فروش ارز به مشتری**، با نام مشتری و کد ملی (اختیاری) و توضیحات
- **بخش مستقل دریافت و پرداخت** (وب و Windows Forms): ثبت دریافت از مشتری و پرداخت به مشتری، مستقل از فرم معامله؛ ارز صندوق و ارز مانده‌ی حساب مشتری جدا انتخاب می‌شوند. صندوق فقط به ارز خودش تغییر می‌کند؛ تسویه در ارز یکسان ۱:۱ و در ارز متفاوت با نرخ شعبه در تاریخ تسویه انجام می‌شود. نرخ ورودی اختیاری و صرفاً اطلاع‌رسانی است.
- **کارمزد ثابت به ریال** برای هر معامله:
  - فروش به مشتری: مشتری «مبلغ ریالی + کارمزد» می‌پردازد.
  - خرید از مشتری: مشتری «مبلغ ریالی − کارمزد» دریافت می‌کند (کارمزد باید کمتر از مبلغ ریالی باشد).
- **ابطال و ویرایش اسناد** (مدیر، یا کاربر شعبه‌ای که مدیر دسترسی لازم را به او داده است؛ بخش «دسترسی‌ها»): معامله، دریافت/پرداخت مستقل، موجودی افتتاحیه و سند دستی قابل ابطال یا ویرایش‌اند. ابطال با **سند معکوس** انجام می‌شود، سند اصلی حذف نمی‌شود و علامت «باطل شده» می‌گیرد. ویرایش مالی، نسخه‌ی قبلی را باطل و نسخه‌ی اصلاحی را جایگزین می‌کند؛ ویرایش اطلاعات توصیفی معامله (نام مشتری، کد ملی، یادداشت) مستقیم انجام می‌شود.
- **ثبت با تاریخ گذشته**: معامله، دریافت/پرداخت مستقل، موجودی افتتاحیه و سند دستی را می‌توان تا ۳۰ روز قبل ثبت کرد (ساعت، ساعت ثبت است). تاریخ آینده مجاز نیست.
- **سند حسابداری دستی** (ثبت فقط مدیر؛ ابطال و ویرایش با دسترسی جدا): سندی با چند سطر متوازن روی حساب‌های فعال (به‌جز حساب‌های موجودی ارز). اگر به حساب `1001` بزند، موجودی صندوق ریال هم تغییر می‌کند.
- **رسید** برای هر معامله (HTML با قابلیت چاپ از مرورگر؛ معامله‌ی باطل‌شده با علامت مشخص نمایش داده می‌شود).
- **گزارش و خروجی Excel** از معاملات، اسناد، اشخاص، هر سرفصل حساب در هر سطح، حساب‌های بانکی نام‌دار و همه‌ی صندوق‌ها؛ گزارش سرفصل امکان مانده تا یک تاریخ یا گردش بازه‌ای و انتخاب ثبت مستقیم/تجمیع زیرحساب‌ها را دارد.
- **ورود تاریخ شمسی** در فیلترهای گزارش و اسناد، مثلاً `۱۴۰۵/۰۷/۰۱` (با `/`، `-` یا `.` و با ارقام فارسی یا انگلیسی).
- **چند شعبه**:
  - مدیر همه‌ی شعبه‌ها را می‌بیند و می‌تواند شعبه‌ی جدید بسازد.
  - کاربر صندوق فقط شعبه‌ی خودش را می‌بیند و فقط در همان شعبه ثبت می‌کند.
  - صندوق‌ها، موجودی ارزی، نرخ‌ها، معاملات و اسناد هر شعبه جدا هستند؛ ارزها و حساب‌ها مشترک‌اند.
- قیمت تمام‌شده‌ی ارز به روش **میانگین موزون** (جداگانه برای هر شعبه) و محاسبه‌ی سود/زیان تحقق‌یافته‌ی هر فروش
- صندوق ریال و صندوق جدا برای هر ارز در هر شعبه؛ موجودی منفی ثبت نمی‌شود
- نرخ خرید و فروش روز برای هر ارز در هر شعبه، همراه با تاریخچه
- سند حسابداری دوطرفه برای هر معامله و رسید/پرداخت مستقل؛ هر سند قبل از ثبت بررسی تراز می‌شود
- دریافت و پرداخت مستقل از معامله با نرخ خرید/فروش شعبه در تاریخ سند ارزش‌گذاری می‌شود؛ نرخ ورود در این فرم فقط اطلاع‌رسانی است و اثری بر ارزش دفتر ندارد. ریال نرخ ثابت یک دارد. برای معاملات، دو روش نرخ مستقیم جفت‌ارز و نرخ مشتق‌شده از نرخ‌های ریالی شعبه در فرم موجود است.
- مانده‌ی حساب مشتری مانع ثبت دریافت/پرداخت نمی‌شود: دریافت ابتدا دریافتنی را کم می‌کند و مازاد را بستانکار/پیش‌پرداخت می‌کند؛ پرداخت ابتدا پرداختنی را کم می‌کند و مازاد را به دریافتنی مشتری می‌برد. پرداخت فقط در صورت کافی‌بودن موجودی صندوق انجام می‌شود؛ ویرایش و ابطال با سند معکوس، سابقه‌ی دفتر را حفظ می‌کند.
- موجودی افتتاحیه‌ی ریال و ارز برای هر شعبه (ثبت فقط مدیر؛ ابطال و ویرایش با دسترسی جدا)
- داشبورد: موجودی صندوق‌ها، ارزش روز موجودی ارزی، سود/زیان شناور، کارمزد و معاملات امروز
- کاربران با دو نقش **مدیر** و **کاربر صندوق**؛ رمز عبور با PBKDF2
- **دسترسی‌های ثبت، ویرایش و ابطال** که مدیر برای معامله، موجودی افتتاحیه، سند دستی و دریافت/پرداخت مستقل به هر نقش در هر شعبه می‌دهد؛ عملیات فقط در شعبه‌ی مجاز ممکن است
- **سرفصل چهار سطحی**: گروه ← کل ← معین ← تفصیلی، با نوع حساب به‌ارث‌رسیده و سند فقط روی حساب‌های تفصیلی یا معین بدون زیرمجموعه (بخش «سرفصل حساب‌ها»).
- **مشتریان مشترک**: هر معامله به یک مشتری ثبت‌شده وصل است؛ ثبت و ویرایش مشتری برای کسانی که وظیفه‌ی «ثبت معامله» دارند (بخش «مشتریان»).

## راه‌اندازی

پیش‌نیازها: **.NET 10 SDK** و **SQL Server 2019** (در CI با سطح سازگاری ۱۵۰ تست می‌شود).

### ۱. اتصال و ساخت پایگاه داده

در هر اجرا، ابتدا خود موتور SQL Server آزمایش می‌شود. اگر اتصال تنظیم‌شده برقرار باشد، برنامه به بانک موجود وصل می‌شود و نسخه‌ی شِما را با آخرین مهاجرت مقایسه می‌کند. اگر اتصال برقرار نشود:

- **ویندوز**: پنجره‌ی راه‌اندازی، SQL Serverهای قابل کشف را فهرست می‌کند؛ می‌توانید سرور/نمونه را انتخاب کنید یا آدرس را دستی بنویسید، سپس نام کاربری و رمز SQL را وارد کنید.
- **وب**: صفحه‌ی `/SqlConnection` همین کار را انجام می‌دهد. در حالت HTTP، فرم رمز فقط از همان رایانه (loopback) باز می‌شود؛ درخواست راه دور باید HTTPS باشد.
- در صورت وجود بانک انتخاب‌شده یا `mojdbN` موجود، همان بانک استفاده می‌شود. اگر بانک لازم موجود نباشد، اولین نام آزاد `mojdb1`، `mojdb2` و ... در موتور SQL ساخته می‌شود و فایل‌های `.mdf` و `.ldf` در `database` کنار فایل اجرایی قرار می‌گیرند.
- SQL Server باید SQL Authentication (حالت Mixed Mode) را فعال کرده باشد و حساب SQL مجوز `dbcreator` یا `sysadmin` داشته باشد. سرویس SQL Server هم باید به پوشه‌ی `database` دسترسی نوشتن داشته باشد. اگر SQL Server روی رایانه‌ی دیگری است، مسیر داده باید برای **سرویس آن موتور SQL** قابل دسترسی باشد؛ صرفاً وجود پوشه روی رایانه‌ی برنامه کافی نیست.
- هر نسخه‌ی تازه‌ی شِما از مهاجرت‌های شماره‌دار همراه برنامه اعمال می‌شود؛ نیازی به اجرای دستی اسکریپت نیست.

نصب دستی اختیاری روی بانک تازه (فقط اسکریپت مرجع):

```bat
sqlcmd -S localhost -E -f 65001 -i database\AccountingSystem.sql
```

یا فایل را در SSMS باز و Execute کنید. این فایل مرجع `AccountingSystem` را با سطح سازگاری ۱۵۰ می‌سازد؛ برنامه‌ی وب و ویندوز به‌طور معمول از مهاجرت‌های جاسازی‌شده استفاده می‌کنند.

### ۲. تنظیم اتصال (اختیاری)

برای اتصال دستی/محیط استقرار می‌توانید رشته‌ی اتصال را در این فایل‌ها تنظیم کنید:

- `src/AccountingSystem.Web/appsettings.json` ← `ConnectionStrings:AccountingSystem`
- `src/AccountingSystem.WinForms/appsettings.json` ← همین بخش

نمونه‌ی اتصال Windows Authentication به سرور پیش‌فرض:

```json
"AccountingSystem": "Server=localhost;Database=AccountingSystem;Trusted_Connection=True;TrustServerCertificate=True;"
```

پس از وارد کردن SQL Login در راه‌انداز، اطلاعات در `%LOCALAPPDATA%\AccountingSystem\sql-connection.bin` ذخیره می‌شود؛ در Windows رمز با DPAPI کاربر جاری محافظت می‌شود. در Unix مجوز فایل و پوشه فقط به همان کاربر محدود است. رمز SQL در لاگ نوشته نمی‌شود.

### ۳. اجرای نسخه‌ی وب

برای توسعه و اجرای محلی:

```bash
dotnet run --project src/AccountingSystem.Web
```

برای اجرای روی سرور (همان خروجی `publish`):

```bash
dotnet publish src/AccountingSystem.Web -c Release -o publish/web
cd publish/web
dotnet AccountingSystem.Web.dll
```

آدرس پیش‌فرض: `http://localhost:5080` (در `appsettings.json` به `0.0.0.0` متصل است تا از شبکه‌ی داخلی هم در دسترس باشد).

- اگر هیچ کاربری ثبت نشده باشد، صفحه‌ی **راه‌اندازی اولیه** نمایش داده می‌شود و اولین کاربر، مدیر سیستم خواهد بود.
- برای دسترسی از اینترنت یا شبکه‌ی ناامن، برنامه را پشت یک Reverse Proxy با HTTPS قرار دهید.

### ۴. اجرای نسخه‌ی ویندوز

```bat
dotnet run --project src/AccountingSystem.WinForms
```

(یا فایل `AccountingSystem.exe` پس از `dotnet publish`). فایل `appsettings.json` باید کنار فایل اجرایی باشد. رسیدها در پوشه‌ی موقت ویندوز ساخته و با مرورگر پیش‌فرض باز می‌شوند.

### ۵. ترتیب کار پس از نصب

1. مدیر را بسازید (اولین ورود).
2. در تب/صفحه‌ی **شعبه‌ها** شعبه‌های لازم را بسازید (کد شعبه: ۱ تا ۱۰ حرف یا رقم انگلیسی، مثلاً `MAIN` یا `B2`). با ساخته شدن هر شعبه، صندوق‌ها و موجودی ارزی همه‌ی ارزها برای آن ساخته می‌شود.
3. برای هر شعبه، **موجودی اولیه** صندوق ریال و ارزها را در صفحه‌ی **صندوق‌ها** ثبت کنید.
4. برای هر شعبه، **نرخ‌های خرید و فروش** را در صفحه‌ی **نرخ و ارزها** ثبت کنید. ارز جدید را مدیر اضافه می‌کند؛ با افزودن ارز، صندوق و موجودی آن برای همه‌ی شعبه‌ها ساخته می‌شود، اما نرخ آن برای هر شعبه جداگانه ثبت می‌شود.
5. کاربران صندوق را بسازید؛ هر کاربر صندوق باید یک شعبه داشته باشد.

## منطق حسابداری

حساب‌ها: `1001` صندوق ریال، `1101-<کد ارز>` موجودی ارز به بهای تمام‌شده، `1201` دریافتنی مشتری، `2101` پرداختنی مشتری، `3001` سرمایه‌ی افتتاحیه، `4001` سود معاملات ارزی، `5001` زیان معاملات ارزی، `4101` درآمد کارمزد معاملات.

| رویداد | سند |
|---|---|
| خرید ارز از مشتری (بدون کارمزد) | بدهکار `1101-X` (بهای ریالی) / بستانکار `1001` |
| خرید ارز از مشتری با کارمزد | بدهکار `1101-X` (بهای ریالی) / بستانکار `1001` (ریال پرداختی = مبلغ − کارمزد) و بستانکار `4101` (کارمزد) |
| فروش ارز به مشتری | بدهکار `1001` (ریال دریافتی = مبلغ + کارمزد) / بستانکار `1101-X` (بهای تمام‌شده)، بستانکار `4001` یا بدهکار `5001` برای سود یا زیان، و بستانکار `4101` (کارمزد) |
| دریافت مستقل از مشتری | بدهکار صندوق ارز دریافت‌شده (`1001` یا `1101-X`)، بستانکار `1201` تا میزان دریافتنی موجود و ثبت مازاد به بستانکار `2101` به‌عنوان پیش‌پرداخت مشتری |
| پرداخت مستقل به مشتری | بدهکار `2101` تا میزان پرداختنی موجود و ثبت مازاد در `1201` به‌عنوان دریافتنی؛ بستانکار صندوق (`1001` یا `1101-X`). پرداخت ارزی با بهای میانگین موزون ثبت و تفاوت ارزش با بهای صندوق در سود/زیان شناسایی می‌شود؛ پرداخت به موجودی کافی صندوق نیاز دارد. |
| موجودی افتتاحیه ارز | بدهکار `1101-X` / بستانکار `3001` |
| موجودی افتتاحیه ریال | بدهکار `1001` / بستانکار `3001` |
| ابطال هر سند | سند معکوس با منبع `VOID` که مانده‌ی خالص سند اصلی (شامل تعدیل‌ها) را خنثی می‌کند |
| تغییر بهای تمام‌شده‌ی فروش‌های بعدی | سند تعدیل با منبع `ADJUST`: موجودی ارز و سود یا زیان فروش به‌اندازه‌ی تفاوت بهای تمام‌شده تنظیم می‌شود |
| تغییر بهای پرداخت ارزی مستقل | سند تعدیل با منبع `CASH_ADJUST`؛ اثر تغییر تاریخچه بر میانگین موزون صندوق را ثبت می‌کند |
| سند دستی | سطرهای دلخواه متوازن با منبع `MANUAL` |

- مبلغ ریالی هر معامله = مقدار × نرخ، به نزدیک‌ترین ریال (نیم به دور از صفر) گرد می‌شود.
- کارمزد **عدد صحیح ریال** و **صفر یا بیشتر** است و در هر معامله جداگانه وارد می‌شود. سود تحقق‌یافته‌ی فروش بدون کارمزد محاسبه می‌شود.
- بهای تمام‌شده‌ی مقدار فروخته‌شده = موجودی بهای تمام‌شده × مقدار فروش ÷ موجودی ارز. فروش کل موجودی، دقیقاً کل بهای ثبت‌شده را خارج می‌کند.
- **بازمحاسبه‌ی تاریخچه**: بهای میانگین موزون هر فروش و پرداخت ارزی به ترتیب زمان وقوع (و ترتیب ثبت برای زمان یکسان) محاسبه می‌شود. با هر ثبت با تاریخ گذشته، ابطال یا ویرایش معامله، دریافت/پرداخت یا افتتاحیه، کل تاریخچه‌ی همان شعبه دوباره اجرا می‌شود. اگر در هیچ لحظه‌ای ریال یا ارز منفی شود، عملیات رد می‌شود و سند مانع نشان داده می‌شود.
- **تعدیل**: اگر بهای تمام‌شده‌ی یک فروش قدیمی تغییر کند، سند تعدیل با تاریخ همان لحظه‌ی ثبت تغییر ثبت می‌شود. سندهای قبلی تغییر نمی‌کنند. گزارش سود معاملات بر اساس مقدار به‌روز شده نمایش داده می‌شود، در حالی که سند تعدیل در روز ثبت آن است.
- **ابطال و ویرایش**: مدیر، یا کاربر صندوق دارای دسترسی مربوط در شعبه‌ی خودش، با دلیل (۱ تا ۲۰۰ کاراکتر) و ثبت کاربر در سابقه (جدول `AuditLog`). سند باطل‌شده حذف نمی‌شود؛ علامت `IsVoided` می‌گیرد و دوباره قابل ابطال نیست. ویرایش مالی سند جدید با پیوند `ReplacesId` به نسخه‌ی قبلی می‌سازد.
- **کنترل همزمانی**: هر ثبت، نسخه‌ی دفتر شعبه (`Branches.LedgerVersion`) را یک واحد بالا می‌برد. اگر کاربر دیگری قبل از شما ثبت کرده باشد، ثبت شما با پیام «اطلاعات در همین لحظه توسط کاربر دیگری تغییر کرده است» رد می‌شود.
- هر معامله یا دریافت/پرداخت در **یک تراکنش** SQL ثبت می‌شود. اگر موجودی صندوق یا بهای تمام‌شده هم‌زمان توسط کاربر دیگری تغییر کرده باشد، تراکنش لغو و پیام «اطلاعات در همین لحظه توسط کاربر دیگری تغییر کرده است. لطفاً دوباره تلاش کنید.» نمایش داده می‌شود.

## سرفصل حساب‌ها (چهار سطح)

ساختار سرفصل درختی و چهار سطحی است. کد هر سطح به کد پدرش وابسته است:

| سطح | نام | مثال | سند می‌گیرد؟ |
|---|---|---|---|
| ۱ | گروه | `1` دارایی‌ها | خیر |
| ۲ | کل | `10` صندوق‌ها | خیر |
| ۳ | معین | `1101` موجودی ارز (زیرمجموعه دارد) / `1001` صندوق ریالی (بدون زیرمجموعه) | فقط اگر زیرمجموعه نداشته باشد |
| ۴ | تفصیلی | `1101-USD` | بله |

- نوع حساب (دارایی، بدهی، سرمایه، درآمد، هزینه) در **گروه** تعیین می‌شود و به زیرمجموعه‌ها به ارث می‌رسد.
- سند فقط روی حساب **فعال و بدون زیرمجموعه** ثبت می‌شود. حساب تجمیعی (گروه، کل یا معینی که زیرمجموعه دارد) سند نمی‌گیرد.
- کد گروه یک رقم (۱ تا ۹) است. کد زیرمجموعه با کد پدر شروع می‌شود و بلندتر از آن است. حداکثر چهار سطح مجاز است.
- حساب‌های **پایه‌ی موتور** (`1001`، `3001`، `4001`، `4101`، `5001` و `1101-<ارز>` که با افزودن هر ارز ساخته می‌شود) در معاملات و سندهای خودکار استفاده می‌شوند. کد، حساب پدر، نوع و وضعیت آن‌ها قابل تغییر نیست و فقط **نام** آن‌ها ویرایش می‌شود. این محدودیت فنی است، چون سندهای خودکار و موتور حسابداری به این کدها و انواع وابسته‌اند.
- حسابی که سند یا زیرمجموعه دارد حذف نمی‌شود؛ برای توقف استفاده آن را غیرفعال کنید (فقط حساب بدون زیرمجموعه غیرفعال می‌شود).
- مدیریت سرفصل فقط برای **مدیر سیستم** است: وب (منوی «سرفصل حساب‌ها») و ویندوز (تب «سرفصل حساب‌ها»).

## مشتریان

- فهرست مشتریان بین **همه‌ی شعبه‌ها مشترک** است. هر کاربر فعالی که به حداقل یک شعبه دسترسی دارد آن را می‌بیند.
- **کد مشتری** (مثل `C0000000012`) را سیستم هنگام ثبت می‌سازد و کاربر آن را نمی‌بیند یا تغییر نمی‌دهد. این کد ستون محاسباتی و پایدار پایگاه داده است، پس حتی `UPDATE` مستقیم SQL هم آن را تغییر نمی‌دهد.
- **اطلاعات مشتری**: نام (الزامی)، کد ملی یا شناسه (اختیاری و یکتا)، شماره‌ی موبایل (حداقل ۱۰ رقم)، تلفن ثابت، شهر، نشانی، دو شماره‌ی شبا (IR و ۲۴ رقم)، دو شماره‌ی کارت (۱۶ رقم) و یادداشت. شبا و کارت هر دو اختیاری‌اند. ارقام فارسی خودکار لاتین می‌شوند و جداکننده‌ها حذف می‌شوند.
- **نمایش شماره‌ی کارت**: در فهرست‌ها فقط چهار رقم آخر دیده می‌شود. شماره‌ی کامل کارت‌ها و شباها فقط در فرم ویرایش نشان داده می‌شود، که برای دارندگان «ثبت معامله» باز است. سرویس داده را به هر عضو فعال می‌دهد؛ اگر بخواهید در سطح سرویس هم محدود شود، باید دسترسی خواندن جدا تعریف شود.
- ثبت و ویرایش مشتری برای **مدیر سیستم** و هر کاربری است که وظیفه‌ی «ثبت معامله» را در **هر** شعبه‌ای دارد.
- **هر معامله** (خرید، فروش و ویرایش آن) باید به یک مشتری ثبت‌شده وصل باشد. معامله بدون مشتری ثبت نمی‌شود.
- معامله نام و کد ملی مشتری را به‌صورت **رونوشت** نگه می‌دارد. تغییر بعدی نام یا کد ملی مشتری، معاملات قبلی را تغییر نمی‌دهد.
- کد ملی یا شناسه اختیاری است، ولی اگر وارد شود برای یک مشتری بیشتر ثبت نمی‌شود. ارقام فارسی و عربی خودکار به لاتین تبدیل می‌شوند.
- در این نسخه مشتری حذف نمی‌شود، تا سابقه‌ی معاملات گم نشود.
- الزامات قانونی شناسایی مشتری (احراز هویت، گزارش به مراجع ذی‌ربط) جداگانه باید بررسی شود (بخش «محدودیت‌ها»).

## طراحی و رابط کاربری

- **وب**: ناوبری گروه‌بندی‌شده (معاملات، حسابداری و، برای مدیر، مدیریت)، کارت‌ها و جدول‌های یکدست، برچسب وضعیت رنگی، پیام‌های موفقیت و خطا، فرم‌های راست‌چین و چیدمان واکنش‌گرا برای صفحه‌های کوچک. فایل سبک `wwwroot/css/site.css` سیستم طراحی برنامه است (رنگ‌ها و فاصله‌ها در `:root`).
- **ویندوز**: فونت و فاصله‌ی یکدست (Tahoma)، دکمه‌های اصلی (ثبت، ذخیره، ایجاد) رنگی، دکمه‌های ابطال و حذف قرمز، و جدول‌های خوانا با ردیف راه‌راه و انتخاب رنگی. این تنظیمات در `Theme.cs` است.
- فونت فارسی از پشته‌ی محلی انتخاب می‌شود (Vazirmatn اگر روی سیستم نصب باشد، در غیر این صورت Tahoma). برنامه به فونت یا منبع خارجی وابسته نیست.
- منوی وب در سه گروه «کار روزانه»، «حسابداری» و «مدیریت» چیده شده است؛ صفحه‌ی فعال مشخص است، نقش کاربر نشان داده می‌شود و لینک پرش به محتوا برای صفحه‌خوان‌ها هست.
- نسخه‌ی ویندوز یک نوار وضعیت پایین پنجره دارد که کاربر، شعبه‌ی دسترسی و نسخه‌ی پایگاه داده را نشان می‌دهد؛ دکمه‌های ثبت و ایجاد آبی، دکمه‌های ابطال و حذف قرمز هستند.
- این تغییرات فقط ظاهر و چیدمان است و روی منطق حسابداری اثری ندارد.

## دسترسی‌ها

- **مدیر سیستم** به همه‌ی شعبه‌ها و همه‌ی وظیفه‌ها دسترسی کامل دارد و برای او نقش شعبه‌ای تعریف نمی‌شود. شعبه، کاربر، نقش و ارز را فقط مدیر سیستم مدیریت می‌کند.
- **کاربر شعبه** می‌تواند عضو چند شعبه باشد. در هر شعبه‌ای که عضو است **یک نقش** دارد. شعبه‌ی اصلی او (`Users.BranchId`) باید یکی از همین عضویت‌ها باشد؛ برای حذف عضویتِ شعبه‌ی اصلی، ابتدا شعبه‌ی اصلی را عوض کنید.
- **نقش** مجموعه‌ای از وظیفه‌هاست و برای هر شعبه جدا تعریف می‌شود. هر شعبه‌ی جدید سه نقش پیش‌فرض می‌گیرد:

| نقش | وظیفه‌ها |
|---|---|
| حسابدار | ویرایش و ابطال معامله و موجودی افتتاحیه؛ ثبت، ویرایش و ابطال سند دستی و دریافت/پرداخت مستقل |
| مدیر شعبه | همه‌ی سیزده وظیفه |
| کاربر صندوق | ثبت معامله و ثبت دریافت/پرداخت مستقل |

- سیزده وظیفه: ثبت معامله (`TRADE_RECORD`)، ویرایش معامله (`TRADE_EDIT`)، ابطال معامله (`TRADE_VOID`)، ثبت موجودی افتتاحیه (`OPENING_CREATE`)، ویرایش موجودی افتتاحیه (`OPENING_EDIT`)، ابطال موجودی افتتاحیه (`OPENING_VOID`)، ثبت سند دستی (`MANUAL_CREATE`)، ویرایش سند دستی (`MANUAL_EDIT`)، ابطال سند دستی (`MANUAL_VOID`)، تنظیم نرخ (`RATE_SET`)، ثبت دریافت/پرداخت (`CASH_TRANSACTION_CREATE`)، ویرایش (`CASH_TRANSACTION_EDIT`) و ابطال آن (`CASH_TRANSACTION_VOID`).
- وظیفه فقط در **شعبه‌ای** معتبر است که کاربر در آن نقشِ دارای آن وظیفه را دارد. مثلاً حسابدارِ شعبه‌ی A نمی‌تواند در شعبه‌ی B معامله را ویرایش کند.
- **مشاهده**: هر عضو یک شعبه، اطلاعات همان شعبه را می‌بیند. کاربر شعبه در گزارش‌ها یک شعبه را می‌بیند (پیش‌فرض شعبه‌ی اصلی)؛ مدیر می‌تواند «همه‌ی شعبه‌ها» را انتخاب کند.
- تغییر نقش، عضویت یا وظیفه‌های یک نقش **همان لحظه** اعمال می‌شود، چون هر بار از پایگاه‌داده خوانده می‌شود و به ورود قبلی وابسته نیست.
- نقشی که به کاربری داده شده باشد حذف نمی‌شود؛ اول آن را از کاربران جدا کنید.
- هر تغییر نقش، عضویت، شعبه‌ی اصلی و وظیفه‌ها در جدول `AuditLog` با کاربر و زمان ثبت می‌شود (`ROLE_CREATE`، `ROLE_PERMISSIONS`، `ROLE_DELETE`، `USER_BRANCH_ROLE`، `USER_DEFAULT_BRANCH`).
- **پایگاه‌داده‌ی نسخه‌ی دسترسی‌های نقش‌دار** (`33e04e4`) به‌صورت خودکار ارتقا می‌یابد و داده‌ها حفظ می‌شوند. جدول قدیمی `UserPermissions` در این نسخه حذف شده است؛ پایگاه‌داده‌های پیش از آن (که `UserPermissions` دارند) ارتقای خودکار ندارند و برنامه آن‌ها را رد می‌کند.

## تصمیم‌های طراحی

این موارد در درخواست صریحاً مشخص نشده بودند و به این شکل پیاده‌سازی شده‌اند:

- **دریافت/پرداخت مستقل مشتری‌محور است**: هر سند به مشتری ثبت‌شده وصل می‌شود و مانده‌ی مشتری صرفاً برای انتخاب حساب مقابل استفاده می‌شود، نه برای رد سند؛ مازاد دریافت/پرداخت به‌ترتیب در پرداختنی/دریافتنی ثبت می‌شود. پرداخت به مشتری همچنان به موجودی کافی صندوق نیاز دارد. این فرم فعلاً برای دریافت عمومی درآمد یا پرداخت هزینه بدون مشتری نیست.
- **تاریخ گذشته تا ۳۰ روز مجاز است** (برای معامله، دریافت/پرداخت مستقل، موجودی افتتاحیه و سند دستی یکسان). بازهٔ ۳۰ روز در `OccurrenceRules.MaxBackdateDays` تعریف شده است.
- **کارمزد ثابت به ریال** است، نه درصدی از مبلغ.
- **رسید** یک رسید داخلی HTML است. اگر برای صورتحساب یا فاکتور رسمی الزام قانونی دارید، آن را جداگانه بررسی کنید.
- **ابطال و ویرایش با دسترسی جداگانه**. کاربر صندوق به‌طور پیش‌فرض ثبت معامله و دریافت/پرداخت مستقل را انجام می‌دهد؛ ثبت افتتاحیه، سند دستی، ویرایش و ابطال را مدیر بر حسب نیاز به نقش می‌دهد (بخش «دسترسی‌ها»).
- **هر ثبت کل تاریخچه‌ی شعبه را بازمحاسبه می‌کند.** برای شعبه‌های با تاریخچه‌ی بسیار بزرگ، باید عکس‌فوری دوره‌ای اضافه شود.

## تست‌ها

```bash
dotnet test tests/AccountingSystem.Core.Tests
```

برای تست‌های یکپارچگی روی SQL Server، رشته‌ی اتصال (با دسترسی ساخت پایگاه داده) را در متغیر `AS_TEST_SQL` قرار دهید. تست‌ها پایگاه داده‌ی `AccountingSystem_IT` را از روی همان اسکریپت می‌سازند و اگر این متغیر تنظیم نشده باشد، بدون خطا رد می‌شوند.

```bash
set AS_TEST_SQL=Server=localhost;User Id=sa;Password=...;Encrypt=False;TrustServerCertificate=True
dotnet test tests/AccountingSystem.Data.Tests
```

در CI (`.github/workflows/ci.yml`):

- تست‌های Core و Data اجرا می‌شوند و خطاها و نتیجه‌ی هر تست به‌صورت annotation گزارش می‌شوند.
- برنامه‌ی وب پس از `publish` اجرا و با `.github/scripts/web-smoke.py` بررسی می‌شود: ورود مدیر، سرو شدن فایل‌های استاتیک، باز شدن صفحات اصلی (از جمله کاربران و شعبه‌ها که فقط مدیر می‌بیند)، و تولید فایل Excel از معاملات و اسناد.

## ارتقا، پشتیبان و بازیابی

### راه‌اندازی اتصال SQL Server
- اگر اتصال تنظیم‌شده برقرار باشد، پنجره‌ی ویندوز/صفحه‌ی وب نمایش داده نمی‌شود و برنامه ادامه می‌دهد.
- اگر اتصال در دسترس نباشد، در Windows، نمونه‌های محلی از رجیستری و سرورهای معرفی‌شده توسط SQL Server Browser کشف می‌شوند (روی سیستم‌عامل‌های دیگر یا وقتی Browser خاموش/UDP 1434 بسته باشد، آدرس دستی لازم است). آدرس دستی مانند `localhost\MOJ` یا `server,1433` نیز پذیرفته می‌شود.
- فرم، SQL Login (نام کاربری و رمز SQL) می‌گیرد و اتصال به `master` را آزمایش می‌کند. بعد بانک موجود را انتخاب می‌کند یا اولین `mojdbN` آزاد را می‌سازد.
- در اولین ساخت، مسیر فایل بانک `AppContext.BaseDirectory/database/mojdbN.mdf` و فایل log هم‌نام است. دسترسی نوشتن سرویس SQL Server به این پوشه ضروری است. برای وب پشت شبکه‌ی عمومی، تنظیم SQL فقط از loopback با HTTP یا از راه HTTPS مجاز است.
- اعتبارنامه بعد از ساخت/ارتقای موفق ذخیره می‌شود: DPAPI در Windows؛ فایل با مجوز محدود کاربر در Unix.

### ارتقای خودکار نسخه
- هر بار که برنامه‌ی وب یا ویندوز اجرا می‌شود، **قبل از هر کاری** نسخه‌ی پایگاه داده (جدول `dbo.SchemaVersion`) با نسخه‌ی برنامه مقایسه می‌شود.
- نسخه‌های باقی‌مانده به ترتیب شماره اجرا می‌شوند و هر نسخه در **یک تراکنش** است. اگر هر بخشی شکست بخورد، همان نسخه برمی‌گردد، پیام خطا نشان داده می‌شود و برنامه بالا نمی‌آید.
- پایگاه داده‌ای که پیش از جدول `SchemaVersion` ساخته شده ولی ساختارش با نسخه‌ی ۱ تا ۵ یکی است، شناسایی می‌شود و نسخه‌های موجودش ثبت می‌شوند؛ **داده‌ها حفظ می‌شوند**. اسکریپت نصب دستیِ نسخه‌ی فعلی نیز هنگام اجرای بعدی به‌عنوان نسخه‌ی ۵ شناسایی می‌شود.
- برنامه در این موارد ارتقا را رد می‌کند و هیچ تغییری نمی‌دهد: نسخه‌ی پایگاه داده از نسخه‌ی برنامه جدیدتر است؛ فایل مهاجرتی که منتشر شده تغییر کرده؛ ساختار ناقص است (اشیای ناموجود در پیام آمده‌اند)؛ یا پایگاه داده پیش از نسخه‌ی دسترسی‌های نقش‌دار است.
- نسخه‌ی مرجع هر پایگاه داده در صفحه‌ی «پشتیبان و بازیابی» (وب) و تب «پشتیبان و بازیابی» (ویندوز) دیده می‌شود.

### پشتیبان خودکار و تنظیمات
- پیش از هر ارتقایی که نسخه‌ای اجرا می‌کند، **پشتیبان کامل** گرفته می‌شود. اگر پشتیبان‌گیری شکست بخورد، ارتقا انجام نمی‌شود.
- در `appsettings.json` بخش `Backup` را تنظیم کنید:
  - `Folder`: پوشه‌ی پشتیبان **روی سرور SQL** (مثلاً `D:\AccountingBackups`). خالی بماند یعنی پوشه‌ی پیش‌فرض SQL Server (`InstanceDefaultBackupPath`). سرویس SQL Server باید به این پوشه دسترسی نوشتن داشته باشد.
  - `BeforeUpgrade`: پیش‌فرض `true`. فقط برای آزمایش روی بانک خالی‌شده یا با مسئولیت خودتان `false` کنید.
- پشتیبان‌ها با `WITH CHECKSUM` و بدون فشرده‌سازی ساخته می‌شوند (سازگار با SQL Server Express).
- برنامه پشتیبان‌های قدیمی را پاک نمی‌کند؛ آن‌ها را خودتان از پوشه یا با SSMS مدیریت کنید.

### ساخت و بازیابی پشتیبان از برنامه (فقط مدیر سیستم)
- وب: صفحه‌ی **پشتیبان و بازیابی**؛ ویندوز: تب **پشتیبان و بازیابی** (فقط برای مدیر دیده می‌شود).
- فهرست پشتیبان‌ها از جدول `msdb` سرور خوانده می‌شود و فقط پشتیبان‌های همین بانک نشان داده می‌شوند.
- **بازیابی** همه‌ی اطلاعات فعلی را با نسخه‌ی پشتیبان جایگزین می‌کند. پیش از آن یک پشتیبان از وضعیت فعلی گرفته می‌شود (نوع `before-restore`) تا بازیابی اشتباه برگشت‌پذیر باشد.
- در بازیابی، بانک در حالت تک‌کاربره قرار می‌گیرد و با `ROLLBACK IMMEDIATE` **همه‌ی کاربران همان لحظه قطع می‌شوند**. پس از بازیابی، اگر پشتیبان قدیمی‌تر باشد، نسخه‌ی پایگاه داده به نسخه‌ی برنامه ارتقا می‌یابد.
- بازیابی فقط برای فایل‌هایی است که در فهرست پشتیبان‌های همین سرور ثبت شده‌اند و نام فایل باید پسوند `.bak` داشته باشد.


## پایگاه داده: SQL Server 2019

- برنامه برای **SQL Server 2019** طراحی و تست شده است. در CI، تست‌های یکپارچگی و smoke test روی SQL Server 2019 با سطح سازگاری ۱۵۰ اجرا می‌شوند.
- برنامه هنگام ساخت پایگاه داده، سطح سازگاری را ۱۵۰ تنظیم می‌کند. اگر بانکی با سطح پایین‌تر دارید، دستور `ALTER DATABASE [AccountingSystem] SET COMPATIBILITY_LEVEL = 150;` را دستی اجرا کنید و سپس برنامه‌ها را دوباره راه بیندازید.
- سازگاری با SQL Server 2016 تست نشده است.

## محدودیت‌ها و کارهای باقی‌مانده

- **پایگاه‌داده‌های پیش از نسخه‌ی دسترسی‌های نقش‌دار** (با جدول `UserPermissions`) ارتقای خودکار ندارند؛ برنامه آن‌ها را رد می‌کند و اشیای ناموجود را نشان می‌دهد.
- بازیابی، کاربران را قطع می‌کند و به دسترسی سرور SQL به فایل پشتیبان نیاز دارد. پشتیبان‌گیری روی SQL Server Express با پوشه‌ی پیش‌فرض آزمایش شده است؛ پوشه‌ی سفارشی باید برای سرویس SQL Server قابل نوشتن باشد.
- بانک‌هایی که پیش از نسخه‌ی دسترسی‌های نقش‌دار ساخته شده‌اند، باید با روش دستی منتقل شوند؛ برنامه آن‌ها را ارتقا نمی‌دهد.
- نقش «حسابدار» در هر شعبه یک نقش پیش‌فرض است که مدیر وظیفه‌های آن را تغییر می‌دهد. نقش سراسری بدون شعبه وجود ندارد؛ مدیر سیستم همه‌ی شعبه‌ها را دارد و برای او نقش شعبه‌ای تعریف نمی‌شود.
- ویرایش و ابطال اسناد و سند دستی فقط از رابط وب و ویندوز انجام می‌شود. حساب‌های پایه‌ی موتور کد و نوع ثابت دارند (بخش «سرفصل حساب‌ها»).
- سند دستی روی حساب‌های موجودی ارز (`1101-…`) مجاز نیست، چون مقدار ارز از معامله و افتتاحیه می‌آید. پرداخت نقدی از صندوق ریال با سند دستی روی `1001` ثبت می‌شود.
- تست‌های CI منطق بازمحاسبه، ابطال، ویرایش، سند دستی و سازگاری دفتر (سندهای متوازن، مانده‌ی صندوق و بهای موجودی) را روی SQL Server 2019 بررسی می‌کنند؛ عملکرد با تاریخچه‌ی بسیار بزرگ هنوز اندازه‌گیری نشده است.
- نسخه‌ی Windows Forms در CI فقط **کامپایل** می‌شود و روی ویندوز واقعی اجرا نشده است.
- رابط وب و ویندوز فقط با کامپایل و تست دود در CI بررسی شده‌اند. ظاهر آن‌ها روی مرورگرهای مختلف و روی ویندوز واقعی آزمایش دستی نشده است.
- الزامات قانونی شناسایی مشتری (احراز هویت، گزارش به مراجع ذی‌ربط) باید با مشاور حقوقی بررسی شود؛ این نرم‌افزار جایگزین آن‌ها نیست.
